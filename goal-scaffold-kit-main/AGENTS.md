## Architecture rules
- Authorization lives in the database (RLS policies, SECURITY DEFINER helpers like has_permission/can_view_ticket); UI checks (Guard, can()) are cosmetic only — never trust them.
- Ticket numbering, status automation, ticket_activity, activity_logs and notifications are Postgres triggers so every client gets the same behaviour.
- Roles are stored only in user_roles; the first registered user becomes super_admin via handle_new_user.
- Ticket SELECT/UPDATE policies use inline column checks (not can_view_ticket) so INSERT ... RETURNING works for new rows.
- Signed-in pages live under src/routes/_app (ssr: false, client-side session gate); customer and staff share the same ticket pages, RLS scopes the data.
- Server-only privileged work (creating auth users) goes in src/lib/admin.functions.ts with requireSupabaseAuth plus a server-side permission check.
- Ticket attachments are uploaded only through the `/api/attachments/upload` endpoint (content-sniffed, size/type checked) and opened via a server function that checks access under RLS and returns a short-lived signed URL; clients have no direct write access to the bucket or attachment rows, which prevents spoofed storage paths.
- Role experience is derived once in auth (`portal`: admin/agent/customer); each portal has its own dashboard route, sidebar groups and CSS theme via `data-portal` — `/dashboard` only redirects to the portal's home.
- Notification realtime is subscribed exactly once in the app shell with a unique channel topic; components only read the notifications query (reusing a subscribed channel name throws).
- Reply-driven status changes set the transaction-local `app.reply_status_change` flag so only the reply notification is sent, not a duplicate status one.
- AI reply drafts are generated by an authenticated server function (permission `tickets.ai_draft` + RLS ticket access) through the AI Gateway; drafts are only ever inserted into the composer, never sent, and internal notes are excluded from the prompt.
- Two sign-in pages share one server function with a `portal` flag: `/login` takes a plain username (non-admins only) and `/admin-login` takes `<username>@<fixed company domain>` (admins only, domain constant in src/lib/signin-domain.ts); the role/page check runs only after the password is verified so the pages never reveal who is an admin, and real account emails are never exposed; self sign-up is disabled and admins create accounts.
- One-time codes (company-email verification, password reset) live in `auth_otps` as salted hashes with no RLS policies; only server functions in src/lib/auth-security.server.ts issue/check them and email them to the verified company email, so no client or admin can read a code.
- First-time setup is enforced in the database: `is_active_user` is false and a restrictive "require account setup" policy blocks every table until `must_change_password` is cleared, which only the server can do (guard_profile freezes setup/verification columns for signed-in users).
- App emails go through src/lib/email.server.ts, which uses whichever mail connector is linked (Gmail first, then Resend); every send is recorded as email.sent/email.failed in activity_logs and a failed send never counts as success.
- Security events are activity_logs rows with entity_type `auth` and metadata {status, username, error}; never put passwords, codes or keys in them.
- Ticket SLA level and priority are always set by a database trigger from the ticket text (classify_sla_level), never by the client, so customers cannot pick their own level.

- Permission catalogue (permissions, role_permissions) is readable by admins only and settings by settings.manage holders; other code must go through SECURITY DEFINER helpers (has_permission, my_permissions).
- Live updates (notifications, chat, presence) need their tables in the supabase_realtime publication; a fresh or remixed database must re-add them via migration.
